# GraphRAG on Graphify — brainstorm

The Dgraph checkout at `/workspace` is an empty stub (`README.md` is the title line, one commit). Graphify is not in this tree: no `graph.json`, no traversal API, no MCP server, no search index. Everything below pressure-tests the idea as specified, taking the plan’s description of Graphify as a claim rather than as code we can see.

## The idea

Keep Graphify as the thing that parses a repository. Tree-sitter already (by the plan’s account) turns a repo into `graph.json`: code nodes, call and import edges, and Leiden communities. A new layer reads that file after the fact, builds a local search index over the code nodes, and answers a natural-language or messy developer query with a small pack of source for a coding agent. Each function, method, or class is embedded together with a one-line sketch of its neighbors, vectors live in sqlite-vec, and the same SQLite file holds an FTS5 keyword index. At query time the two ranked lists are fused, a handful of seed nodes are walked one or two hops across the graph, and the walk is trimmed to a token budget. The AST engine stays where it is. This is a retrieval front end for an existing graph, aimed at agent context, with an eval harness meant to keep the extra machinery honest.

## What is worth keeping

The split is the right one. Parsing, node spans, and edges are a different problem from “which of these nodes should the model read,” and replacing a tree-sitter graph with a vector database throws away the only high-precision structure code actually has: names, containment, and calls.

Locate-then-expand matches how code changes. The function that matches the question is often not the function that must be edited. Callers, the interface they implement, and one callee that owns the invariant are the context. A flat top-k of chunks cannot say that. A seed plus a typed neighborhood can.

The ablation shape is the other piece to protect. “Grep, then raw code vectors, then vectors of graph-enriched text, then a fused list plus a hop” is a real sequence of claims. Each step has a reason to be false. A harness that can reject a step is more valuable than the index.

A few smaller choices are also sound. Prefer EXTRACTED edges over inferred ones when spending tokens. Treat the packed prompt, not an unbounded ranked list, as the object the agent consumes. Invalidate embeddings from the bytes that were embedded, so a later incremental indexer has a correct key. Keep the index local and file-shaped once the design settles, because a coding tool that needs a side-car vector service will not get used on a laptop. None of those require UniXcoder, a 768-wide schema, or a particular fusion formula.

## Assumptions that may be wrong

**UniXcoder at 768 dimensions is a current code retriever.** `microsoft/unixcoder-base` is a 2022 encoder, about 125M parameters, hidden size 768, context on the order of a thousand tokens, strongest on the CodeSearchNet languages (Python, Java, JavaScript, PHP, Ruby, Go). It is a plausible local baseline. It is a weak default against embedders trained as retrievers, including the plan’s own alternative, `jina-embeddings-v2-base-code` (768-d, much longer context), and against later local code embedders with instruction prefixes. API embedders (Voyage Code and the current OpenAI and Cohere lines) are another class entirely if the machine is allowed to send code off-box. Hard-coding 768 into `semantic_index.db` welds the index to one checkpoint. The schema wants a model id and a dim that are allowed to change, with a full rebuild accepted as the migration.

**Mean-pooling that checkpoint produces a search vector.** The usual Hugging Face recipe — mean of the last hidden state, sometimes with attention masking — is not the same object as UniXcoder’s reported code-search setup, which depended on a contrastive fine-tune and a specific token representation. Mean-pooling the base model mixes the signature, the body, the docstring, and whatever neighbor names were prepended. That can be fine. It can also dilute the only distinctive tokens in a short method. Pooling is an experimental factor, not a default to lock in step 1.1.

**sqlite-vec and FTS5 in one file is “zero infrastructure.”** One SQLite file next to `graph.json` is a good end state for a local tool. sqlite-vec is still a loadable extension that has to match the SQLite build on every developer machine; the file does not travel to a machine that lacks the extension. FTS5’s default `unicode61` tokenizer splits on underscore and does not split camelCase, so `verify_access_token` and `verifyAccessToken` are different queries. That is not symbol search until the tokenizer (or a generated symbol field) is designed. At repo scale, tens of thousands of 768-d float vectors are an easy brute-force scan; a monorepo of hundreds of thousands of symbols is a different latency story, and vec0’s exact scan should be timed before it is the architecture. Two virtual tables in one database also want a story for concurrent readers (the MCP process) and a writer (the post-build hook), and for what happens when `graph.json` is replaced and the `.db` is not.

**Reciprocal rank fusion of cosine and BM25 is the right combiner.** RRF is a reasonable first fusion because cosine and BM25 are not on one scale. With the usual constant `k = 60`, a rank-1 keyword hit outscores a vector-only hit that landed at rank 8. That favors exact names, flags, and error strings, which is what you want for those queries, and it buries a paraphrase that BM25 missed. Equal fusion assumes the two lists are equally trustworthy on every query. They are not. A symbol-shaped query should lean lexical; a bug-report paragraph should lean semantic; a stack trace wants exact frame matching before either ranker. Cutting each list at 20 and then keeping 3–5 seeds also sets a hard recall ceiling: if the true node is 21st on both lists, no amount of BFS will see it. RRF belongs in the ablation as a baseline fusion, beside “vector only,” “BM25 only,” and a trivial router, not as the definition of the engine.

**Putting one-hop context inside the embedding helps.** The proposed payload (file, symbol, callers, callees, then the body) is early fusion. The steelman is real: a query that names a behavior in a neighbor can still land on the right function, and internal code with no docstring gets a few extra words of intent. The costs are easy to miss. The embedder’s context is short, so caller lists push the body off the end of the window and the vector represents the boilerplate that survived truncation. A hub (“called by” forty sites) becomes a bag of other people’s names and will match queries about those people. Any edge change alters the payload hash, so adding one call site re-embeds the caller and, if the template is symmetric, the callee. Later, BFS walks the same edges again and the prompt pays for the neighborhood twice. Early fusion and late expansion are two uses of one signal. The plan’s raw-versus-enriched comparison is exactly the test; the architecture should not assume the enriched side wins. If it wins only by stuffing neighbor names into the vector, a late feature (a graph score, or expansion after a raw-code hit) is the cleaner mechanism.

**“Graphify’s BFS” is a thing we can call.** BFS on an adjacency list is a few dozen lines. The assumption that fails is product-shaped: that Graphify already exposes seed-in, hops-out, with edge types, direction, and a degree cap. This checkout cannot confirm node ids, EXTRACTED versus INFERRED, Leiden output, or any traversal helper. If `graph.json` is only nodes and edges, Phase 3 is a new walker plus a policy, and the policy is the work. Unweighted two-hop BFS from a seed that calls `log`, `get`, or `run` will swallow a subsystem. “Hops = 2” without edge filters, a per-seed fan-in cap, and a ban on high-degree identifiers is a dump, not retrieval. Direction matters too: bugs often want callers (who must change) more than callees (who already implement something). A single undirected BFS treats those as the same neighborhood.

**Leiden communities are part of the design.** They show up in the structural layer and then never again. Either they are a real signal — subsystem membership, a way to bound a walk, a unit you can summarize — or they are an expensive decoration. Code graphs are ambiguous input to Leiden: an import graph clusters packages, a call graph clusters features, and a mixture clusters neither. Until someone looks at a community and recognizes a subsystem, retrieval should not wait on clustering, and the architecture slide should stop implying the communities are load-bearing.

**“Incremental git-diff sync” and a payload hash are one idea.** They are two different mechanisms that the plan’s step title collapses. A content hash of the embedded string is the right invalidation key: re-embed when those bytes change. A git diff is only a hint about which files to re-parse. Diffs miss dirty trees, generated files, and nodes whose bodies were unchanged. File-level diffs also over-invalidate: one edited line does not change every function in the file if the hash is per node. The hash over-invalidates in a different way if it covers the early-fusion payload, because neighbor churn rewrites hashes of untouched functions. The step also says to re-embed changed and new nodes, and does not say to delete nodes that disappeared, so the index grows ghosts. None of this works until node identity survives an edit. If Graphify’s id is a line range, every insertion above a function is a delete plus an insert, and “incremental” is a full rebuild with extra bookkeeping. Stable ids (path, kind, qualified name) plus mutable spans are a precondition, not a Phase 2 optimization. Freezing the payload template matters just as much: one wording change invalidates every hash on purpose.

**coir-eval on CoSQA stands in for repository retrieval.** CoSQA (and COIR around it) measures whether an embedder matches a natural-language query to a standalone snippet, mostly Python, without the rest of a repository sitting next to it as distractors. That is a fair gate. A model that cannot do CoSQA will not do this product. A model that leads CoSQA can still fail here, because the hard cases are near-duplicate methods, identifier-heavy internal code, and answers that are a set of nodes rather than one function that paraphrases the question. NDCG@10 on CoSQA is a different task from Recall@5 over Graphify node ids in one repo. Report the gate in its own column. Do not let it bless the pipeline. Repository-level sets (patch-linked benchmarks in the CodeRAG-Bench / SWE-bench family) are closer to the product, and they bring their own mess: gold labels are hunks, not node ids.

**Thirty to fifty hand labels can rank the system.** They can debug it. They cannot separate four configurations. On forty queries a recall swing of several points is noise, bootstrap intervals will be wide, and one author writing queries against a graph they just designed will ask questions the index can answer. A single relevant `node_id` is the wrong label shape whenever the honest answer is “these four functions and this test.” SWE-bench Lite does not fix that by itself: mapping a gold patch onto Graphify spans is a second annotation problem (hunks that cover a class, a method, and a file-level constant). Use a small hand set for error analysis, stratified by query shape. Derive the numbers you would quote from automatic set-valued labels, and say how the mapping was done.

**Graph-Expanded Recall@5 measures expansion quality.** As defined — the gold node sits within one or two hops of the top three hits — the metric rises whenever the walk gets bigger, including a walk through import edges or through `log`. On a connected graph a two-hop neighborhood of a popular node covers a startling fraction of the repo, so a lucky bad seed still scores. It also scores when the packer then drops the gold node to satisfy a token budget, which is the failure the agent actually feels. The metric has no precision term and no baseline. A degree-matched random walk, or “expand, but only along import edges,” can post a similar number. Expansion has earned its keep only if, at a fixed token budget, the packed set contains more of the relevant nodes than the seeds alone, and more than a dumb neighborhood of the same size.

## Failure modes

**Chunk boundaries.** `start_line`–`end_line` on a tree-sitter node is not automatically a retrieval unit. Class nodes swallow their methods, so the same body is embedded twice, once as a generic class vector and once as a method, and both compete for budget. Nested functions, decorators, and the docstring that sits just outside the span fall out of the slice. The plan’s filter (function, method, class) drops constants, error strings, SQL, config, and migrations, which is where bug reports often point. A generated parser or a thousand-line function is a node only in the syntactic sense.

**Huge nodes.** UniXcoder will silently truncate. The surviving prefix is often imports, a license comment, or argument parsing, and that vector will never match the behavior at the bottom of the function. The index needs an explicit policy: skip above a token cap, embed signature plus docstring plus a head of the body, or split into spans that still point at a parent id for the walk. “We stored a 768-d vector” does not mean the node is searchable.

**Call-graph noise.** A tree-sitter call edge is usually a name occurrence, not a resolved binding. `get`, `run`, `execute`, `clone`, and `error` then connect unrelated definitions. Interface methods, callbacks, reflection, and overloading make the true target a different node from the syntactic one. Tests call almost everything, so “called by” is half test harness. BFS treats every such edge as a reason to spend tokens. If EXTRACTED means “the parser saw a call expression,” it is still low precision, and the plan’s trust in EXTRACTED over INFERRED needs a counted sample before it is a ranking rule.

**INFERRED versus EXTRACTED.** Inferred documentation links can be useful side context and still be poison inside a walk: they are a second retrieval system hiding in the graph, with unknown precision. The plan says to prioritize EXTRACTED edges and attach inferred doc nodes. Those are different operations, and the packer has to treat them as different budgets. If inferred edges are traversed at hop 1 they crowd out real callees. If “inferred” also covers unresolved call targets, they should not be walked until someone has measured how often they point at the right definition.

**The query is a bug report, not a symbol.** “Invoice save NPEs when tax id is empty after the 2024 migration” shares few tokens with the function that is wrong, and it may not sit near that function in a snippet embedder’s space either. The discriminative tokens are in a log line, a fixture, or a config key the node filter discarded. Stack traces want a frame-to-symbol join first; prose similarity is the fallback after exact frames miss. Hybrid search helps only when at least one leg hits. Both legs miss together when the relevant text was never indexed.

**Token budget.** Five seeds, hop two, no fan-in cap, is not a context pack. Deduping nodes does not decide which neighbor to keep. Hubs fill the window first because there are more of them. The agent then sees a wide, shallow dump and still misses the one method that matters. The packer is the product. It needs an order: edge type, direction, degree penalty, diversity across seeds, and a hard token stop. Until that order exists, hops and `top_k` are not parameters worth exposing on an MCP tool.

**Stale index.** `graph.json` and `semantic_index.db` are two artifacts with no atomic publish. Line-based ids make the drift worse: the vector points at a node id whose span has moved, or at a deleted node the updater never removed. Branch switches and a dirty working tree do the same thing quietly. An agent will treat a stale pack as the code. The MCP tool should be able to say “index built at this graph hash” and refuse a mismatch. Incremental update is unsafe until deletes, renames, and id stability are specified.

**Multi-language.** Tree-sitter being multi-language does not make one embedder multi-language. A UniXcoder vector space built from CodeSearchNet will mis-rank Rust, Kotlin, C++, C#, and often TypeScript-specific idioms, and it will happily match the shared English of `error` and `data` across languages. Call and import structure are different graphs in Go interfaces, Rust traits, and C++ templates than in the Python example in the plan. FTS tokenization and Leiden both change shape in a polyglot monorepo. An eval that only runs CoSQA will not see any of this. The first benchmark repo’s languages are the real scope; everything else is a hope.

## Alternatives

Each of these is a branch worth one experiment, not a literature tour.

Raw-code embeddings, with the graph used only after the seed is chosen, may beat early fusion and make incremental indexing track body edits. Symbol-level units (qualified function and method names) should be the default document, with a file-level vector only as a fallback when the answer is not inside one function. Late fusion — a graph feature or a walk scored separately from the embedding — keeps “what this code says” and “what it connects to” from fighting over one short vector. Community summaries are the classic GraphRAG use of Leiden: retrieve a subsystem blurb, then search inside it, which is the feature this plan names and then leaves idle. A small cross-encoder reranker on a fused top 30 is often where hybrid rank becomes “the function I would edit,” and it is cheaper to try than a new graph schema. Existing lexical stacks (ripgrep used well, Zoekt-style trigram and symbol indexes, Sourcegraph, and SCIP or a language-server call hierarchy) are the floor a local embedder has to beat on names, error strings, and resolved calls; where a language server is already running, its call hierarchy may be a better expander than unresolved tree-sitter edges.

## What to measure

Keep CoSQA or a small COIR slice as a model gate: NDCG@10 and MRR, one pooling recipe, reported once per checkpoint. Do not mix those numbers into the repo table.

On the repo, label sets of nodes, not a single id. Stratify queries into at least three buckets: exact or near symbol, ordinary natural-language question, and bug-report or stack trace. For each bucket report seed Recall@5 and MRR.

Score the pack at fixed budgets (for example 2k, 4k, and 8k tokens): recall of the relevant set inside the pack, and token-weighted precision of what was packed. Record median nodes and tokens emitted so a configuration cannot win by pasting half the repo.

Redefine graph-expanded recall so it can fail. Fix the edge types and the direction that count as a hop. Compare against the seeds with no expansion and against a degree-matched random neighborhood of the same size. If expansion does not beat both at the same budget, it does not ship.

Fill the holes in the four-way ablation. The plan’s last cell turns on BM25 fusion and one-hop expansion in the same step, so a win cannot be attributed. The matrix wants lexical-only, raw vector, enriched vector, hybrid fusion without a walk, and raw vector plus a walk, before the full combination. Run the lexical floor twice if Graphify’s current grep is a naive substring scan: once as “what the product does today,” and once as a serious identifier baseline, so vectors have to beat a grown-up word matcher.

Count the operational facts that explain a pretty recall number: fraction of nodes truncated, fraction of gold nodes the filter cannot represent (non function/method/class), median degree of the seeds you returned, fraction of walked edges that are EXTRACTED, re-embed rate when one typical commit lands, and stale-id rate after a rebuild. Publish bootstrap intervals over queries. With a few dozen hand labels, the honest output is a pile of failures grouped by mode, not a winner.

## First slice

Start with the eval harness, cut down, plus a throwaway probe. Do not start by building the indexer, and do not start by building hybrid search.

The claims that justify sqlite-vec, the enrichment template, RRF, and BFS are empirical, and they are entangled. An index built first freezes the payload and the dimension before those claims are tested, and every payload edit throws the index away. A search engine built first gets tuned against vibes, and unbounded hop-recall will flatter it. The question the rest of the plan stands on is narrower: on one real Graphify graph, with set-valued labels, does a vector of the raw node text beat a serious lexical baseline at Recall@5, and does a stupid one-hop pack at a fixed budget beat the seeds alone?

So the first slice is: take one repository Graphify can already parse; dump `graph.json`; write down the actual node id, the span fields, and the edge-type enum that file contains today. Hand-label about twenty queries against those ids, mixed across the three query shapes, with multiple relevant nodes where that is the truth. Implement the metrics above, including the lexical floor and a budgeted pack. Embed raw slices with one local model in memory (brute-force cosine is enough at this size), no sqlite-vec, no FTS5, no fused ranks, no enriched payload. If Graphify has no BFS helper, write the walk in the harness and record the edge policy next to the score. The harness is done when it can print a table that would reject a later idea.

If raw vectors do not beat the lexical floor on this repo, stop. Enrichment and RRF are not allowed to paper over that. If they do beat it, the next experiment — still on this harness — is raw versus enriched text, and only then a lexical leg. sqlite-vec, incremental hashing, git diffs, Leiden, hop-2, the token packer’s ranking policy, and the MCP tool all wait until a configuration wins on budgeted set recall by a margin the interval can see.

What to defer, explicitly: the CoSQA bake-off as a blocker (run it in parallel once, as a gate, when a model is about to be kept), SWE-bench mapping until spans are understood, 768-d schema design, early-fusion payload wording, Reciprocal Rank Fusion, production incremental sync, community summaries, and `semantic_graph_search` as an MCP tool. Exposing hops and `top_k` to an agent before the packer has a policy will launder graph noise into every client.

## Decisions

The open questions are closed. Items 1–4 are the user’s answers. Items 5 and 6 are recommendations the user asked for, and each one names what would reverse it. Facts about Graphify below were read from the repository at commit `35d1d2038b9e9d470f117bf8f2473d415b5f5358` (branch `v8`, package `graphifyy` 0.9.106) and checked by running `graphify update` on a six-file Python sample. They replace the "claim, not code" stance of the opening paragraph for everything listed here.

**1. Source of truth: [Graphify-Labs/graphify](https://github.com/Graphify-Labs/graphify), pinned by commit.** Python, Apache-2.0, CLI `graphify` and `graphify-mcp` (`pyproject.toml`), library pipeline `detect → extract → build → cluster → export` ([`ARCHITECTURE.md`](https://github.com/Graphify-Labs/graphify/blob/v8/ARCHITECTURE.md)). It moves daily and its README says "no embeddings, no vector store" ([`README.md`](https://github.com/Graphify-Labs/graphify/blob/v8/README.md)), so the semantic layer is a separate package, not a patch to the pipeline. What `graph.json` holds today, which is what the harness is designed against:

- Nodes: `id`, `label`, `file_type`, `source_file`, `source_location` (`"L16"`, a start line only), `community`, `community_name`, `norm_label`, plus private flags (`_callable`, `_origin`, `_py_return_type`). No end line, no `kind`, no qualified name, no source text. Methods are labelled `.name()`, so `.__init__()` appears once per class. Docstrings become separate `rationale` nodes joined by `rationale_for`.
- Edges: `source`, `target`, `relation`, `confidence` (`EXTRACTED`, `INFERRED`, `AMBIGUOUS`), `confidence_score`, `source_file`, `source_location`, `weight`, sometimes `context`. The relation set is open (the sample shows `contains`, `method`, `calls`, `inherits`, `imports`, `imports_from`, `uses`, `references`, `rationale_for`), not an enum; [`validate.py`](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/validate.py) only checks `confidence`. The file says `"directed": false`, but arc order is the direction; a plain `node_link_graph()` load loses it, so read it through `paths.load_node_link_graph()` (`ARCHITECTURE.md`, "Edge direction in graph.json").
- Ids are not line ranges. They are the path stem plus symbol names, normalized ([`ids.py`](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/ids.py), `extractors/base.py::_file_stem`), so an insertion above a function does not move its id. They do change when a file moves or is renamed, and a normalization collision is salted by declaration order (`DeclIdRegistry`). Stable enough for incremental work; not stable across renames.
- Calls are partly resolved, not bound. In the sample, same-file calls are `EXTRACTED` and cross-file calls came out `INFERRED` at 0.85. Python receiver typing exists but is documented as best-effort (`ARCHITECTURE.md`). Treat every `calls` edge as a heuristic until the harness counts a sample.
- Communities: Leiden only if the optional `graspologic` extra is installed, Louvain otherwise ([`cluster.py`](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/cluster.py), the `leiden` extra in `pyproject.toml`). A plain install, including mine, produced Louvain. Record which one ran.
- Traversal and search already exist: undirected BFS that refuses to expand through hubs (degree at least `max(50, p99)`), depth 1–6 (default 2), a roughly 3-characters-per-token budget (default 2000), `--seed`, and a reverse walk in `graphify affected` ([`serve.py`](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/serve.py) `_bfs` and `_subgraph_to_text`; [`affected.py`](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/affected.py)). Search is lexical: IDF-weighted tokens, a trigram index, label and path tiers (`serve.py` `_score_query`). That is not a naive substring scan, so it is the real lexical floor.
- Extension is by library or fork: per-language extractors under `graphify/extractors/`, a `resolver_registry.py` seam for cross-file resolution, and `exporters/`. There is no plugin API for node fields. Adding a field means editing each extractor’s `add_node` (for Python, `extractors/engine.py`) and bumping the AST cache schema.

**2. Graphify may change, minimally.** The one change the plan needs is an `end_line` (and a `kind`) on code nodes. Without spans the harness cannot slice raw text and cannot map a patch hunk onto a node, which is the only automatic label source. Ids need no change. Edge-type enums and resolved calls wait until the harness shows which relations carry signal; resolving calls is a language-server-sized project, not a field. Until a Graphify change lands, derive spans in the harness by re-parsing `source_file` at the recorded start line with tree-sitter. Do not make the slice wait on a fork.

**3. Consumer: an agent context pack, nothing else.** The product is one function from a query to a packed string under a fixed token budget. `seed_count`, `hops`, `top_k`, and the RRF constant are internal constants the harness tunes; they are not arguments anyone else sees. There is no MCP tool in this slice and no human search box. If an agent integration is built later, it takes one argument, the query. Graphify’s own `query` exposes `--depth` and `--budget`; do not copy that surface.

**4. Embedding is local-only, with a small Hugging Face model.** No API embedders, which also closes the plan’s earlier Voyage and OpenAI branch.

Primary: **`nomic-ai/CodeRankEmbed`**. 136.7M parameters, 768-d, 8192-token context (`config.json`), MIT. It is a bi-encoder contrastively fine-tuned (InfoNCE) on the 21M-pair CoRNStack set, initialized from Arctic-Embed-M-Long, so it is a retriever, not a repurposed masked LM. Its model card reports CoIR NDCG@10 of 60.1 and CSN MRR 77.9, against 58.4 for Jina-Code-v2 and 54.4 for CodeSage-Small. It is the only candidate here with a published number on the benchmark the project chose, and it is small enough for a laptop CPU. Costs: queries need the literal prefix `Represent this query for searching relevant code: `; the model needs `trust_remote_code=True` and executes `modeling_hf_nomic_bert.py` from the model repo, so pin the revision hash; the training data is Python, Java, JavaScript, Go, PHP and Ruby, so anything else is unproven.

Fallback: **`Qwen/Qwen3-Embedding-0.6B`**. 595.8M parameters, 1024-d with Matryoshka truncation to 32, 32k context, Apache-2.0, instruction-aware, last-token pooling. The Qwen3 report gives MTEB(Code, v1) 75.41 (Tables 3 and 9, [arXiv 2506.05176](https://arxiv.org/abs/2506.05176)). That is not a CoIR average and cannot be compared with 60.1: the task mixes differ, and its training list names CodeSearchNet, which the benchmark rows test. It is about 4x the parameters, still laptop-feasible for a repo-sized index, and wider on languages. Switch to it if the gate or the repo table shows CodeRankEmbed failing outside its six languages or on bug-report-shaped queries.

Rejected: `nomic-ai/nomic-embed-code` (7.07B parameters, not small); `Salesforce/SFR-Embedding-Code-400M_R` (CoIR 61.9, but CC-BY-NC-4.0 and "research purposes only"); `jinaai/jina-code-embeddings-0.5b` (CC-BY-NC-4.0); `google/embeddinggemma-300m` (gated, Gemma terms, 2048 context, MTEB(Code, v1) 68.76); `jinaai/jina-embeddings-v2-base-code` (161M, Apache-2.0, 8192 context, older, 58.4 CoIR); `codesage/codesage-small-v2` (130M, 1024-d, needs an added EOS token, no CoIR figure on its card). If non-commercial terms are acceptable, SFR-400M and the Jina 0.5B model move up; nobody has said they are.

**5. First corpus: [`encode/httpx`](https://github.com/encode/httpx) at tag `0.28.1`, commit `26d48e0634e6ee9cdc0533996db289ce4b430177`.** BSD-3-Clause. At that tag: 23 package files, 8,828 lines, 446 `def`s; 37 test files, 8,923 lines, 688 `def`s. That is a graph in the low thousands of nodes: big enough for near-duplicate distractors, small enough to audit by hand. Why this one:

- It is pure Python, a language with documented receiver-type call inference in Graphify (`ARCHITECTURE.md`), so the first result is less likely to be dominated by parser quality.
- Its sync and async twins (`Client`/`AsyncClient`, `HTTPTransport`/`AsyncHTTPTransport`, the auth flows, the streams) are the near-duplicate failure mode from the failure-modes section, in a form you can count.
- Tests are half the code and call everything, so the "called by is mostly test harness" problem shows up on day one.
- `CHANGELOG.md` references about 349 distinct issue and PR numbers, which is the raw material for set-valued labels: fix commit, hunks, nodes at the parent commit.

Limits, stated up front: a popular repo is probably in every embedder’s training data, so absolute numbers flatter; it is one language, so nothing about polyglot behavior is learned; `master` is a different, newer line than the tag, so never run the harness on a moving head. I did not run Graphify on the repos I passed over (`psf/requests`, `pallets/flask`, `pallets/click`), so their node and edge counts are not measured; the choice rests on file and line counts and on the twin structure. A TypeScript repo is the second corpus, after the first table exists.

**6. Correctness and COIR.** The user wants better code retrieval, and COIR is the chosen benchmark. COIR measures one thing: whether a model matches a query to a standalone snippet. Ten datasets, eight tasks, about two million documents in total ([CoIR README](https://github.com/CoIR-team/coir), [paper](https://arxiv.org/abs/2407.02883)). It has no repository around the snippet, no node ids, no packing. So it is a model gate and gets its own column; it cannot say the pipeline retrieves better code, and the repo table is where that is decided. Gate procedure:

- Run COIR once per checkpoint, for CodeRankEmbed and Qwen3-Embedding-0.6B only, with the pooling and prefix recipe frozen. Report NDCG@10 per dataset and the average, never merged with repo numbers.
- The first use of the gate is a harness check: reproduce CodeRankEmbed’s published 60.1 within about 1.5 points. If it is lower, the prefix, pooling, or truncation is wrong, and nothing downstream is trusted until that is fixed. The CoIR and MTEB leaderboards differ in setup ([CoIR issue 17](https://github.com/CoIR-team/coir/issues/17)), so use the CoIR harness, not MTEB’s, for this number.
- The full corpus is too large for a laptop CPU in reasonable time. Run the small-corpus datasets locally and the rest on a rented GPU, or skip them and say so; do not report a partial average as the CoIR score.
- Pass means "reproduces, and is not beaten by the other checkpoint by a margin the repo table would care about." The gate rejects broken models. It does not pick the winner; the repo table does, on set recall at a fixed budget.

What counts as correct on the repo remains the earlier answer: label sets of nodes, scored as set recall inside a fixed-budget pack. Labels come from two sources, kept separate: fix commits mined from `CHANGELOG.md` references, mapped to nodes at the parent commit (needs spans, decision 2), and about twenty hand-written queries in the first-slice shape. Hand labels are for error analysis and are written by someone who can audit `httpx`; the mined set carries the numbers.

## Implications for the first slice

The "First slice" section above stands, with these changes now that the answers are in.

- Build the graph now. Question 8 is closed: run `graphify update` with `GRAPHIFY_BACKEND=none` on `httpx` at the pinned commit. Record the Graphify commit and version next to every result. "Dump `graph.json` and write down the node id, span fields, and edge enum" is done (decision 1); the first task is instead spans: derive `end_line` per node and count how many nodes cannot be spanned.
- No sqlite-vec, no FTS5, no fused ranks, no enriched payload, as before. Local-only does not change this. The extension-loading question is deferred, not answered. Embed raw slices with CodeRankEmbed in memory, brute-force cosine, 768-d treated as a parameter, query prefix frozen.
- No MCP and no exposed knobs. The harness entry point is `pack(query, budget)`. 2k, 4k, and 8k are evaluation conditions, not agent-facing arguments.
- The lexical floor is not "grep." Floor one is Graphify’s own scorer, which is what the product does today. Floor two is a serious identifier baseline: split camelCase and snake_case, BM25 over identifiers and docstrings. Vectors have to beat both.
- Do not write a walk from scratch first. Graphify’s `_bfs` (undirected, hub cutoff, depth 2) is the baseline expander, and the "if Graphify has no BFS helper" branch of the first slice does not apply. The harness’s typed, directed, degree-capped walk is the challenger. Both run at the same budget against the seeds alone and against a degree-matched neighborhood. Record the edge policy next to the score, including how many walked edges are `EXTRACTED` versus `INFERRED` in this graph.
- COIR is a separate column in a separate table, run once per checkpoint, in parallel with harness work, never a blocker (decision 6). It does not appear in the ablation matrix.
- Add a fourth query bucket to the three already named: sync/async twin queries, where the gold set is both twins or one named twin. It is the cheapest honest test of near-duplicate handling, and it exists in `httpx` by construction.
- Counters get concrete targets: share of `.name()` labels that are ambiguous across classes, share of `calls` edges that are `INFERRED`, share of mined gold nodes that have no span or are not a function, method, or class, Leiden versus Louvain, and rename-induced id churn between the two commits compared.
- Read `graph.json` through Graphify’s loader for edge direction, and do not import other Graphify internals; the layer stays a separate package that consumes the file.
- Still deferred: sqlite-vec, FTS5, RRF, enrichment wording, incremental sync and hashing (ids are line-independent, so this is cheaper than the earlier section feared, but rename handling is unsolved), Leiden-based summaries, SWE-bench mapping, and any MCP tool. A Graphify patch for `end_line` and `kind` goes upstream if it is small, and the harness keeps its tree-sitter fallback until then.
